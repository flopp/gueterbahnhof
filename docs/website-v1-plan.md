# Website v1 plan

## Goal

Publish a useful, mobile-first information website for residents and visitors
of Freiburg's Quartier Güterbahnhof. Visitors should be able to understand the
area, find local amenities, and get reliable details for a selected place.

The first release is a static site generated by the existing Go command-line
program. Content is maintained in the repository and the generated files can
be deployed to a static web host using the project's planned `scp` workflow.

## V1 scope

### Included

- A responsive landing page introducing the area and linking to the directory
  and map.
- A directory of published shops, restaurants, and other useful amenities.
- A detail page for each amenity, showing its name, category, description,
  address, opening hours when available, and selected images when available.
- A map page showing the area and published amenities, with links to their
  detail pages, using an interactive Leaflet map and OpenStreetMap-based
  tiles.
- German as the primary language for the interface and content.
- Repository-managed content that can be added and edited without changing
  generator code.
- A build that validates content and produces a complete static output tree.
- Basic metadata, accessible navigation, and usable core content without
  JavaScript.

### Not included

- User accounts, submissions, an administration interface, or a backend.
- Live opening hours, browser geolocation, routing/directions, reviews, or
  third-party map APIs beyond the selected OpenStreetMap tile service.
- Search, filtering, or additional languages in the first release.
- Automated scraping or a promise that listed information is continuously
  up to date.

These are deliberately deferred to keep the initial release straightforward to
build, host, and maintain. Revisit them based on user feedback and maintenance
needs.

## Recommended implementation sequence

### 1. Confirm content and map inputs

- Confirm place coordinates and select an OpenStreetMap tile provider whose
  usage policy and expected traffic are appropriate for the site. Identify
  applicable attribution requirements.
- Use the supplied
  [`data/gueterbahnhof.geojson`](../data/gueterbahnhof.geojson) polygon as the
  neighborhood boundary; confirm its extent and display style in the map.
- Decide the initial categories and collect a small, verified set of places.
- Maintain the initial interface and place content in German; confirm which
  contact, opening-hours, and image fields are available and who will maintain
  them.
- Obtain or select a project name, logo, and visual assets if they exist.

**Exit criteria:** The first content set has a source/verification date,
coordinates and the supplied boundary are checked, the tile provider and
attribution are selected, and missing data can be represented honestly in
German.

### 2. Define content and output contracts

- Adopt the JSON content format described in
  [website-v1-technical.md](./website-v1-technical.md).
- Define required fields, optional fields, slug rules, image paths, and map
  coordinate conventions.
- Read and validate the area GeoJSON as part of the build, and decide whether
  a place without coordinates appears in the directory only or also in a
  separate unlocated list on the map page.
- Establish that invalid content or missing referenced assets fail generation.

**Exit criteria:** A sample data file and tile-provider configuration can be
reviewed before template implementation begins.

### 3. Implement and test the generator

- Separate command-line handling, content loading/validation, page rendering,
  and static asset copying into focused Go packages as the implementation
  grows.
- Render templates with `html/template`; do not interpolate content into HTML
  strings.
- Generate the landing page, directory, map page, and one detail page per
  published place.
- Add unit tests for parsing and validation and integration tests that build a
  small fixture site into a temporary directory.
- Keep the output deterministic so changes are reviewable and repeatable.

**Exit criteria:** `go test ./...` passes, invalid input returns a non-zero
exit status with a useful message, and the fixture build contains working
internal links and copied assets.

### 4. Build the first visual release

- Implement the mobile-first layout and page patterns in
  [website-v1-design.md](./website-v1-design.md).
- Add the Leaflet map, render the GeoJSON boundary and verified place markers,
  fit the initial view to the boundary, and provide visible attribution and a
  readable place list.
- Add image alternatives, keyboard-accessible navigation, responsive images,
  German language metadata, and a no-JavaScript fallback for core content.
- Review on narrow and wide viewports and test with keyboard navigation.

**Exit criteria:** Directory and detail content are readable on phones; the
interactive map works where JavaScript and tiles are available; an equivalent
place list and all core content remain usable if they are not.

### 5. Verify content and release

- Check every place's name, address, category, description, hours, and links
  against its cited/recorded source.
- Check all images and map/tile-provider attribution requirements and
  reasonable page performance.
- Generate a clean output directory and inspect it as a static site.
- Deploy to a staging location using the documented `scp` approach, then check
  routes, assets, and links on the deployed site.
- Record the content review date and a maintainer contact or update process.

**Exit criteria:** The generated site works from the intended host path, the
content is reviewed, and the maintainer knows how to rebuild and publish it.

## Release acceptance checklist

- [ ] Landing page, directory, map, and individual place pages are generated.
- [ ] Every published place has a stable, unique slug and a detail page.
- [ ] Navigation, directory, and place details work without JavaScript.
- [ ] The Leaflet map shows verified places and a readable list equivalent.
- [ ] The supplied GeoJSON boundary is shown and frames the initial map view.
- [ ] Map attribution is visible and the tile provider's usage policy is met.
- [ ] The interface and maintained content are in German.
- [ ] Missing optional information is omitted or labeled as unknown, never
  fabricated.
- [ ] Invalid content and broken asset references fail the build clearly.
- [ ] The site is usable on a phone, with keyboard navigation and meaningful
  image alternatives.
- [ ] Output is static and can be served without a Go runtime.
- [ ] Build/test and staging deployment steps are documented.

## Risks and open decisions

- **Map service availability and policy:** OpenStreetMap-based tiles rely on a
  network service. Select a provider whose usage policy supports the site's
  expected traffic, show attribution, and preserve a useful text list when
  tiles are unavailable.
- **Information freshness:** Opening hours and business details change. Keep
  source and review-date metadata so maintainers can identify stale entries.
- **Sparse initial data:** Allow optional fields and launch with a smaller,
  accurate directory rather than filling gaps with assumptions.
- **Asset rights and performance:** Prefer project-owned or explicitly licensed
  imagery; resize images before publishing and retain required attribution.
- **Hosting path:** Confirm whether the site is hosted at a domain root or a
  subpath before choosing URL generation and the exact `scp` destination.
